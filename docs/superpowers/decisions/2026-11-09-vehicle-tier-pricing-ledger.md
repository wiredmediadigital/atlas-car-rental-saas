FINDING 1 — T2's concurrency test ("refuses the second of two concurrent inserts at the last slot") cannot be run as two real sessions: the database tests replay migrations on a single in-memory PGlite connection.
Ruling: express it as proof the gate is INSIDE the write — the trigger fires on the insert itself, with no client-side pre-check anywhere in the path — rather than as two parallel sessions. Why: a BEFORE INSERT trigger is inherently inside the write, so its location is the property that matters and is the property that is testable here. Cost if wrong: the suite proves where the gate sits, not its behaviour under true parallelism; a genuine race would need an integration test against a real Postgres, which this project does not have.

FINDING 2 — T2's per-row trigger and T3's up-front batch check can both fire for an import, and the trigger's single-vehicle message would surface instead of the batch message naming free slots.
Ruling: in the batch path T3 refuses BEFORE any row is inserted, so its own message is what reaches the user; T2's trigger stays as the backstop and is never the message source for an import. Cost if wrong: a 40-row import would show the single-vehicle sentence — confusing, not unsafe, and caught by T3's "names the number of free slots" test.
